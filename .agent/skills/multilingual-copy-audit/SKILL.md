# Metronome Multilingual Copy Audit

## Use This When

- 新增或修改任何用户可见文字。
- 调整 `src/i18n.ts` 中的文案、标签、说明、按钮文案、空状态、提示语。
- 审查“同一个东西在不同地方叫法不一样”的问题。
- 把技术表达改得更适合新手理解，但又不能失去准确性。
- 翻译或同步多语言文案时，需要检查跨语言语义是否对齐。
- 即使本次只改了单一语言，也要回看其它语言是否因此出现明显不一致。

## Do Not Use This When

- 任务重点是纯视觉样式、主题 token、布局或交互动效。
- 文案只是临时占位，当前还没有真实产品语义。
- 任务是营销 slogan、品牌口号、法律条款、隐私政策。
  这类内容可以参考本技能的简洁原则，但不要强行套用产品 UI 文案的写法。

## Inputs

- 用户请求和当前改动范围。
- 用户可见源码：
  `src/i18n.ts`, `src/components/**`, `README.md`, `src/components/SEO.tsx`
- 当前界面真实入口和功能映射：
  `.agent/skills/ui-map/SKILL.md`
- 项目术语表：
  `.agent/skills/multilingual-copy-audit/references/term-registry.md`

## Source Of Truth

- 以当前产品真实功能和运行时代码为准，不要为文案硬造不存在的行为。
- 以“同一功能在所有语言里表达同一件事”为底线，不把某个语言版本当成可以单独漂移的例外。
- 同一功能的首选叫法，以术语表为准。
- 如果术语表和当前 UI 冲突，先检查真实界面，再决定是改文案还是更新术语表。

## Working Rules

- 每次生成或修改用户可见文字后，都做一次本技能复查，再结束任务。
- 先统一“这是什么”，再优化“怎么说得更好懂”。
- 优先使用目标语言里自然的产品表达，不要机械照搬源语言句法；必要时可以重写句子，只要功能语义不变。
- 标题、按钮、标签优先短而稳；说明文案优先直接解释动作和结果。
- 对新手友好不等于过度口语化；保留必要专业词，但第一次出现时要让人能看懂。
- 同一概念在同一层级里不要混用多个近义说法。
- 默认把所有已存在的语言都纳入检查范围，不要只审中文。
- 若这次改动引入了新的稳定术语，顺手更新术语表。
- 检查标点是否统一，尤其是括号、冒号、引号、斜杠前后空格。
- 不要在同一语言里混用全角括号 `（ ）` 和半角括号 `()`。
- 文案必须对应当前真实 UI：如果控件已经从 slider 变成 wheel、按钮文案已经改名、入口位置已经变化，所有语言都要同步更新。
- 若因时间或范围限制无法一起修完所有语言，结束前明确标注剩余语言风险。

## Review Order

1. 先确认文案对应的功能、按钮、弹窗、设置项是否准确。
2. 检查文案里提到的控件名、方向、位置和交互是否与当前 UI 一致。
3. 对照术语表检查同一概念是否使用同一叫法。
4. 检查是否能让第一次使用的人立刻明白“这是什么、怎么用、会发生什么”。
5. 删除无意义重复、内部术语堆叠、解释过长的部分。
6. 检查同组文案的句式、语气、标点、长短是否协调。
7. 逐语言对照，确认不同语言保持同一层语义，不出现一边说功能、一边说实现细节。
8. 检查括号和其它标点是否统一，不混用全角 / 半角写法。

## Hard Checks

- 不要把实现细节写成用户说明，除非它会直接影响使用。
- 不要把“功能名”和“说明句”写成两个不同概念。
- 不要把同一术语在标题、正文、按钮、弹窗里来回换词。
- 不要在新手向说明里突然引入未解释的缩写或术语。
- 不要让不同语言把同一功能说成不同层级的东西，例如一边写“功能作用”，另一边写“实现方式”。
- 不要沿用已经过时的控件叫法或旧信息架构，例如明明是滚轮却还写成 slider。
- 能说“做什么”和“怎么操作”时，少说抽象评价。
- 避免空泛词：
  “灵活”“智能”“高效”“便捷”“专业级”
  除非它们后面有具体行为支撑。
- 中文默认用自然产品语气，不写生硬直译，不堆英文括注。
- 中文文案默认统一使用全角括号 `（ ）`；如需保留英文缩写，可写成 `中文（TAP）`。
- 英文及大多数西文文案默认使用半角括号 `()`
- 同一语言内不要混用两套括号风格，除非该语言的排版习惯明确要求。
- 同组条目尽量保持同样的信息结构：
  名称 + 作用 / 操作 + 结果

## Help Modal Pass

处理 `HelpModal` 或类似新手导览时，额外检查：

- 顺序是否贴合真实界面阅读路径。
- 每条是否只讲一个点，不把两个概念硬塞进一条。
- 标题是否能和界面上的真实入口对上号。
- 描述是否优先解释用户能做什么，而不是内部机制。
- 若同一区域已有快捷键说明，不要在正文里重复一整遍，只保留必要提示。
- 同一组说明里的括号形式是否统一。

## SEO & Semantic Pass

处理 SEO 或首屏语义文本时，额外检查：

- 把 `title`、`description`、`keywords`、隐藏 `h1`、JSON-LD `name` / `description` 当成一个整体联查。
- 不要只改搜索摘要而忘记同步页面内的语义标题，反之亦然。
- SEO 文案可以更偏搜索表达，但不能和站内功能名冲突。
- 若某语言为了更自然改写了 SEO 标题，需同步检查对应的隐藏 `h1` 是否仍然同层语义。
- 若 JSON-LD 里引用了功能列表或说明，确认它们仍然是当前产品真实存在的功能。

## Multi-Language Parity

- 默认检查所有现有语言，不因本次只改了中文就跳过其它语言。
- 先确定基准语义，再同步各语言，不要各写各的。
- 基准不是逐字对译，而是每个语言版本都像该语言里的真实产品文案。
- 若只精修了单一语言，也要逐项检查其它语言是否已经产生明显偏义、术语漂移或标点风格漂移。
- 发现跨语言无法在本任务内一起修完时，明确标注：
  `parity risk remains`

## Output Expectations

- 如果任务是 review：
  先给不一致、歧义、冗余、对新手不友好的点，再给建议改法。
- 如果任务包含改文案：
  汇报这次统一了哪些术语、删掉了哪些冗余表达、还剩哪些跨语言风险。
- 若新增或变更了稳定术语，说明是否已更新术语表。
